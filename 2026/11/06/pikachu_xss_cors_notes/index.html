2.2 CORS 的作用

  • XSS：攻击者控制的 JavaScript 是否能在目标页面上下文中执行。
  • CSRF：浏览器是否可能借用用户的登录状态发出请求，以及服务端是否会执行该请求。
  • CORS：浏览器是否允许某个跨源页面读取响应内容。

CORS 校验失败时，服务器可能已经收到并处理请求，但浏览器会阻止调用方 JavaScript 读取响应。CORS 不是阻止所有跨源请求的通用防火墙。

4. Image Beacon 实验 Payload

下面保留你提供的 Payload 结构。它从指定 API 读取 JSON 中的 token 字段，并通过 new Image() 触发一个指向 Beacon 地址的 GET 请求；异常分支发送 CORS_FAIL 标记。

5. Payload 逐段解释

5.1 配置 API 与 Beacon 地址

  • api：8098 上的模拟 Token 接口。
  • beacon：VPS 上用于接收实验信号的 URL。

5.2 d.token 的含义

d 是 response.json() 解析得到的 JavaScript 对象；d.token 对应 API JSON 响应正文中的 token 字段。当前靶场接口应只返回固定虚拟 Token，以便在自建环境中观察整个数据流。encodeURIComponent() 用于对参数值进行 URL 编码。

5.3 new Image() 与 Image Beacon

  • new Image()：在 JavaScript 中创建一个图片对象，不要求把它插入页面 DOM。
  • .src = ...：设置图片资源地址，浏览器会尝试向该地址发起 GET 请求。
  • ?d=：查询参数名称，接收端可以从 URL 查询字符串中看到该参数。
  • encodeURIComponent(d.token)：对 d.token 进行 URL 编码，避免空格、加号、斜杠等字符破坏 URL 结构。

这种方式通常称为 Image Beacon（图片信标）。它可以触发浏览器请求，但 JavaScript 不能通过这个 Image 对象读取 VPS 的响应正文或 HTTP 状态，因此应以 VPS 访问日志判断请求是否到达。

Image Beacon 仍可能受到页面 CSP 的 img-src 指令、DNS、TLS 证书和网络连通性影响。URL 查询参数可能被写入 Web 访问日志、代理日志或监控系统；因此本实验只使用固定虚拟 Token。

5.4 请求 Token API

  • fetch()：发起 HTTP 请求。
  • credentials: 'include'：跨源请求时尝试携带符合浏览器规则的凭证。
  • 它不保证 Cookie 一定发送，也不能绕过 Cookie 的 Domain、Path、SameSite、Secure 等限制。

5.5 检查 HTTP 状态并解析 JSON

response 是 Fetch API 的 Response 对象。response.ok 表示 HTTP 状态码是否处于成功范围（通常为 200–299）。response.json() 读取响应正文并解析 JSON。

5.7 异常处理与失败 Beacon

.catch() 会捕获前面 Promise 链中的异常。常见原因包括网络失败、CORS 阻止脚本读取响应、JSON 解析失败等。因此 CORS_FAIL 是脚本作者设置的失败标记，并不能证明根因一定是 CORS。

6.2 Token API 响应头示例

对于带凭证的跨源请求：

  • Access-Control-Allow-Origin 必须明确指定允许的来源，并与请求的 Origin 匹配。
  • Access-Control-Allow-Credentials: true 表示服务器允许凭证模式下的跨源访问。
  • 不能使用 Access-Control-Allow-Origin: * 来开放带凭证响应的读取。
  • Burp Repeater 手动构造请求不能单独证明浏览器可读取响应，必须在真实浏览器中验证。

7. 请求头、响应头与响应正文中的 Token

位置 示例 说明

8. Cookie 与 HttpOnly

  • HttpOnly 阻止页面 JavaScript 通过 document.cookie 直接读取该 Cookie。
  • HttpOnly 不代表浏览器永远不会在请求中携带 Cookie。
  • credentials: 'include' 表示 Fetch 请求尝试包含凭证，但不会绕过 Domain、Path、SameSite、Secure 等限制。
  • Cookie 不按端口隔离，但主机名、协议、Cookie 属性和浏览器隐私策略仍会影响发送行为。

9. Image Beacon 与 POST 接收接口的区别

对比项 Image Beacon fetch(..., {method: 'POST'})
常见方法 GET POST
数据位置 URL 查询参数 请求正文
接收端读取 服务端读取查询参数 服务端读取请求正文
读取接收端响应 Image 对象不能读取响应正文 取决于同源策略或 CORS
常见限制 CSP img-src、网络、TLS、URL 长度 CSP connect-src、CORS（当需要读取跨源响应时）、网络
隐私注意 URL 参数可能进入 Web 访问日志、代理日志等 请求正文也可能被服务端日志或中间件记录

不要把真实凭证放在 URL 查询参数中。URL 更容易出现在访问日志、代理记录和监控系统中。本实验仅发送固定虚拟标记。

10. 常见误区与排查

现象 可能原因 检查方向
Repeater 返回 200，但浏览器报 CORS Repeater 不执行浏览器 CORS 校验 用 Chrome Network 和 Console 验证
请求的 Origin 是 8098 请求可能不是从预期的 8099 页面发起，或 Repeater 手动改错 检查实际页面地址和浏览器抓包
API 返回 200，但 JS 读不到 JSON CORS 响应头不匹配，或凭证 CORS 配置不完整 检查 Allow-Origin、Allow-Credentials
Cookie 没有发送 Cookie 属性或浏览器策略不允许 检查 Domain、Path、SameSite、Secure 和 credentials
VPS 没有 Beacon 日志 地址错误、DNS/TLS/网络失败，或 CSP 不允许图片来源 检查浏览器 Network、VPS Web 日志和 CSP 报告
失败 Beacon 被标记为 CORS 失败 .catch() 也会捕获网络和 JSON 解析异常 使用“请求或解析失败”这类中性标记，再结合 Console 排查
API 能读到 Token，但 VPS 没有记录 API 读取成功不代表图片请求一定抵达 检查 Beacon URL、img-src、DNS、TLS 和 VPS 日志

推荐验证顺序

  1. 确认 8099 原有 XSS 页面能执行无害测试代码。
  2. 确认 8098 API 返回固定虚拟 JSON。
  3. 在 Chrome Network 中观察从 8099 发起、目标为 8098 的请求。
  4. 确认请求 Origin 为 http://192.168.217.1:8099。
  5. 确认响应 Access-Control-Allow-Origin 与该来源匹配。
  6. 确认浏览器允许实验页面读取 JSON 中的固定虚拟 Token。
  7. 单独检查 VPS 是否收到固定实验 Beacon 标记。
  8. 切换为安全 CORS 配置，重复测试并比较浏览器行为。

11. 修复建议

  1. 对 CORS Origin 使用严格白名单，不要无条件反射任意 Origin。
  2. 对需要凭证的跨源请求，只允许明确、必要且受信任的来源。
  3. 不要在不必要的接口中返回会话 Token 或长期有效凭证。
  4. 对敏感操作实施 CSRF 防护、权限校验和合理的请求方法设计。
  5. 修复 XSS 根因：对输出进行上下文相关编码，避免将不可信输入作为 HTML 或脚本执行，并部署适当的 CSP。
  6. 使用短时、最小权限的 Token，并支持撤销和轮换。
  7. 测试结束后关闭漏洞模拟模式，清理实验 Cookie 和日志。

复习口诀： XSS 看“能否执行脚本”；CSRF 看“能否借用登录状态发请求”；CORS 看“跨源脚本能否读取响应”；Image Beacon 看“浏览器是否发出了图片 GET 请求”；Token 的具体位置则要区分请求头、响应头和响应正文。
